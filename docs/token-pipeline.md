# Token Pipeline

> Context for Jacob (or anyone building the shared design system infrastructure). This explains where tokens live today, how they're structured, and where the gaps are.

---

## Where tokens live right now

| File | Format | Role |
|---|---|---|
| `app/tokens/tokens.json` | W3C DTCG (Tokens Studio–compatible) | Machine-readable token source — colors, radius, spacing, elevation, typography |
| `app/tokens/colors.css` | CSS custom properties (`--md-sys-color-*`) | Authoritative CSS output — what the prototype actually reads at runtime |
| `app/tokens/spacing.css` | CSS custom properties | Spacing tokens |
| `app/tokens/typography.css` | CSS custom properties | Typography tokens |
| `app/tokens/fonts.css` | `@font-face` declarations | Self-hosted Barlow, Roboto Slab, Material Symbols |
| `app/tokens/sd.config.mjs` | Style Dictionary v4 config | Build config (see Current State below) |
| `docs/design-system-tokens.json` | JSON (human + machine readable) | Full token manifest with Flutter mappings and role descriptions — the richest reference doc |
| `docs/design-system.md` | Markdown | Human-readable reference guide |
| `docs/flutter-handoff.md` | Markdown + Dart snippets | Flutter ThemeData mapping and component handoff |

## Current state of the pipeline

**CSS is the live source of truth, not `tokens.json`.**

The prototype reads `app/tokens/colors.css` directly at runtime. That file is maintained by hand — it's not generated by any build step. When a token changes, `colors.css` is edited directly, and then `docs/design-system-tokens.json` and the other docs are updated manually to match.

`app/tokens/sd.config.mjs` runs Style Dictionary, but only for JSON → JSON output (Tokens Studio round-tripping). It does not generate the CSS. The comment at the top of the config says this explicitly.

So the current data flow looks like:

```
Hand-edited → colors.css  ──→  prototype (runtime)
Hand-edited → tokens.json  ──→  Style Dictionary  ──→  tokens/generated/tokens.json (Tokens Studio only)

Docs updated manually to stay in sync with colors.css:
  docs/design-system-tokens.json
  docs/design-system.md
  docs/flutter-handoff.md
```

**There is no automated sync between any of these.** Everything is kept in sync by convention, not by tooling.

## What Jacob should know before redesigning this

### 1. Token naming convention

Tokens follow M3 ColorScheme naming where possible: `--md-sys-color-{role}`. The prefix is intentional — it maps directly to Flutter `ThemeData` and Figma variable names, so all three platforms can share the same name.

The main groups in `tokens.json`:
- `color.dark.*` — dark surface scale (void → tertiary)
- `color.text.*` — text hierarchy
- `color.neonindigo.*` — primary interactive / brand color (CSS: `--md-sys-color-neonindigo-*`)
- `color.indigo.*` — secondary actions (CSS: `--md-sys-color-indigo-*`)
- `color.brand.*` — coral (CTA), teal (data viz), pink (accent), recording
- `color.semantic.*` — success, warning, error, info (each has light/base/dark)
- `color.data.*` — chart series colors
- `color.alpha.*` — transparent overlays
- `color.ext.*` — extended palette for data viz / tags
- `color.neutral.*` — true neutral scale

### 2. Light mode exists

`colors.css` defines both a dark mode (the default) and a light mode (under a `[data-theme="light"]` + `prefers-color-scheme: light` block). `tokens.json` currently only contains dark mode values. If the pipeline generates CSS from `tokens.json`, light mode tokens need to be added.

### 3. The CSS token names don't directly match DTCG key paths

The DTCG file uses `color.neonindigo.base` → the CSS token is `--md-sys-color-neonindigo` (no `-base` suffix). Style Dictionary transforms will need to handle this mapping — the base variant drops the `-base` suffix, light/dark variants keep their suffix.

### 4. `docs/design-system-tokens.json` is the richest reference

If Jacob needs to understand what every token does and how it maps to Flutter, `docs/design-system-tokens.json` is the place to start. It has role descriptions, WCAG ratings on text tokens, and Flutter `ThemeData` field mappings for every color.

## The goal state (as understood from conversation)

Jacob is figuring out where to house the token source so that **Web (Next.js CSS), Flutter, and Figma can all pull from the same place** without manual syncing.

The most likely path from where things are today:

1. **`tokens.json` becomes the single source** (W3C DTCG format, already structured for Tokens Studio)
2. **Style Dictionary generates CSS** (`colors.css`, `spacing.css`, etc.) instead of those being hand-edited
3. **Tokens Studio** reads/writes `tokens.json` and syncs to Figma variables
4. **Flutter** either reads a Style Dictionary output or references `tokens.json` directly via a Dart code-gen step

The `docs/design-system-tokens.json` Flutter mapping (`"flutter"` fields on each token) exists to support step 4 — those fields describe which `ColorScheme` role each token maps to.
